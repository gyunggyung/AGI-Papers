---

강화학습(RL) 과정에서 실제로 모델이 변경되는 양은 아주 적습니다. 그렇다면 바뀔 부분만 작게 요약해서 들고 있으면, 메모리를 훨씬 덜 먹지 않을까요?

7B 모델 자체의 가중치 용량은 14GB에 불과합니다. 하지만 이 모델을 풀 파인튜닝하려면 가중치 변화량(기울기)과 Adam 옵티마이저 상태를 저장하느라 56GB가 넘는 메모리가 추가로 필요합니다. 추론은 거뜬히 돌아가는 서버에서도 RL 학습만 켜면 메모리 부족(OOM)으로 뻗어버리는 이유입니다.

최근 NVIDIA 연구진이 발표한 논문 "LoGRA: Scaling LLM Reinforcement Learning with Low-Rank Gradient Sketches"는 옵티마이저와 행렬 곱셈 순서 하나를 바꿔 이 메모리 병목을 해결합니다.

1. 1점짜리 피드백에 거대한 변화량 창고는 사치다

SFT는 모델이 내뱉는 모든 단어마다 정답을 일대일로 대조하며 빽빽하게 고칩니다. 반면 수학이나 추론 RL은 수천 단어짜리 긴 풀이가 끝난 뒤 "맞았다(1점) / 틀렸다(0점)"라는 단 하나의 결과만 알려줍니다.

고작 이 단순한 신호 하나를 반영하자고, 수십억 개 파라미터 전체의 변화량 창고를 메모리에 일일이 다 띄워두는 건 심각한 낭비입니다.

2. 곱셈 순서만 바꿔서 처음부터 요약본만 만든다

예를 들어 7B 모델 안에는 약 200개(28개 레이어 x 7개)의 가중치 행렬이 들어있고, 행렬 1개의 크기를 4096 x 4096(숫자 약 1,677만 개)이라고 해보겠습니다. 풀 파인튜닝을 할 때는 이 행렬 1개당 64MB짜리 변화량 창고가 필요하고, 모델 전체로는 수십 GB가 쌓입니다.

LoGRA는 역전파 수식에서 행렬을 곱하는 순서(결합법칙으로 동일)만 살짝 바꿨습니다.

- 기존 방식: [미분값 4096x1024] x [입력값 1024x4096]을 먼저 곱해 4096x4096(64MB)짜리 거대 변화량 행렬을 만든 뒤 압축하려고 하니, 이미 메모리가 터집니다.
- LoGRA 방식: 뒤쪽의 [입력값 1024x4096] x [압축행렬 4096x64]를 먼저 곱해 차원을 확 줄인 뒤 미분값과 곱합니다. 이렇게 하면 중간에 64MB짜리 거대 행렬을 거치지 않고, 처음부터 64분의 1 크기인 4096x64(1MB)짜리 얇은 요약본(Sketch)만 바로 만들어집니다.

학습하는 동안에는 이 1MB 요약본만 가볍게 들고 있다가, 모든 계산이 끝나고 실제 모델을 고치는 맨 마지막 순간에만 원래 크기(64MB)로 잠깐 펼쳐서 원본 가중치에 더하고 지워버립니다.

3. LoRA보다 메모리는 반토막, 성능은 풀 파인튜닝

"그냥 LoRA를 쓰면 되지 않나?" 싶지만 구조와 메모리 효율이 완전히 다릅니다. 1.5B 모델(랭크 256) 기준 LoRA는 평균 13.21GB를 썼지만, LoGRA는 절반 수준인 7.18GB만 사용했습니다(45.6% 절감).

- 어댑터가 없는 풀 파인튜닝: LoRA는 원본 모델을 얼리고 옆에 보조 부품(어댑터)을 붙여, 그 부품의 연산 기록과 AdamW 상태를 따로 유지하느라 메모리를 꽤 먹습니다. 또한 보조 부품의 좁은 공간에만 갇혀 학습합니다. 반면 LoGRA는 보조 부품 없이 매 스텝 요약 방향(무작위 압축행렬)을 바꿔가며 원본 모델 전체에 직접 더하기 때문에, 메모리는 덜 쓰면서 제약 없는 풀 파인튜닝을 수행합니다.
- 가벼운 옵티마이저와 통신: 무거운 Adam 대신 요약본의 가로줄(Row) 평균만 기록하는 초경량 RowAdam이나 순수 SGD를 씁니다. 학습된 가중치를 문제 풀이(Rollout) 엔진으로 보낼 때도 무거운 모델 전체가 아니라 얇은 요약본(스케치)과 시드 번호만 전송해 통신 병목까지 줄입니다.

4. 안전벨트(Predicted-KL)와 27B 단일 서버 완주

원본 모델을 직접 건드리다 보면 자칫 값이 너무 크게 바뀌어 기존 언어 능력까지 망가질 수 있습니다. 그래서 연구진은 가중치를 더하기 직전에 "이번 업데이트를 적용하면 다음 단어 확률이 얼마나 흔들릴까?"를 미리 계산(Predicted-KL)해, 위험하다 싶으면 보폭을 자동으로 줄여주는 안전장치를 달았습니다.

Qwen2.5-Math, Qwen3.8-27B에 바로 적용한 결과를 보시죠.

- 1.5B 모델: 기존 풀 튜닝 대비 메모리를 21.8% 아끼면서(9.18GB -> 7.18GB), 수학 정답률(MATH-500)은 오히려 63.77%에서 67.87%로 4.1%p 올랐습니다. 요약 과정에서 불필요한 노이즈가 걸러진 덕분입니다.
- 7B 모델: 메모리를 45.7% 절감(31.82GB -> 17.29GB)하면서 풀 튜닝과 유사한 정답률(풀 튜닝 72.48% vs LoGRA 72.33%)을 유지했습니다.
- 27B 모델: H100 8장 단일 서버에서 기존 풀 튜닝은 시작하자마자 OOM으로 터졌지만, LoGRA는 GPU당 51.5GB 메모리만으로 1,100스텝 이상 완주하며 고난도 추론 점수를 39.7%에서 65.5%까지 끌어올렸습니다.

다만 요약하고 안전벨트(KL)를 계산하는 과정 때문에 스텝당 업데이트 속도는 LoRA보다 약간 느립니다(10.63초 vs 11.31초).

마치며:

메모리가 부족하면 어쩔 수 없이 LoRA로 타협하던 관성에서 벗어나, 변화량을 요약해서 들고 있다가 마지막에 펼쳐서 더한다는 단순한 발상으로 풀 파인튜닝의 벽을 낮춘 연구입니다.

앞으로 RL 과정에서 자주 쓰이지 않을까 싶은 멋진 방법론을 만든 논문입니다.

그리고 최근에 리뷰를 한 "Do We Need Adam?" 논문에서와 같이 RL에서는 AdamW가 적합하지 않다는 것은 이번 논문에서도 확인할 수 있었습니다.

다만 논문에서 실험마다 RowAdam과 순수 SGD를 섞어 썼는데, 두 옵티마이저 중 무엇이 더 나은지에 대한 실험은 없고 Muon 등 최신 옵티마이저와의 비교도 없는 것은 아쉽네요.
