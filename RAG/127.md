---

이전 글에서도 언급했듯이, 에이전트 메모리 시스템을 만든다며 LLM이 원본을 요약하고 가공하는 방식은 문제가 발생하기 쉽습니다. 오히려 원본을 그대로 찾아내는 기본적인 RAG가 더 뛰어나죠. 이 현상을 다시 살펴보고, 단순한 2단계 RAG가 가장 뛰어난 결과를 보여준다는 논문이 나왔습니다.

UIUC와 칭화대학교 등 연구진이 발표한 논문 "Memory Tax: Dissecting the Net Value of Agent Memory"를 소개합니다. 참고로 이 논문은 2026년 10월 25일에 공개 됐고, 바로 전에 리뷰한 "Is Complex Agentic Memory Always Needed?"은 10월 22일에 공개됐습니다.

1. 메모리의 양날의 검: 메모리 이득과 메모리 세금

연구진은 원본 대화를 요약하거나 그래프로 재구성하는 과정을 '원본으로부터의 변형'이라고 정의합니다. 이 변형은 두 가지 상반된 결과를 낳습니다.

- 메모리 이득(Memory Benefit): 흩어진 사실을 묶거나 선호도를 정리해 주어, 기본 RAG는 틀리지만 메모리 시스템은 맞히는 문제들입니다.
- 메모리 세금(Memory Tax): 반대로 정보를 요약하고 가공하느라 중요한 단서가 날아가거나 변질되어, 기본 RAG는 쉽게 맞히는 문제를 메모리 시스템이 틀리게 되는 손실입니다.

실험 결과, 상당수 메모리 시스템에서 이득보다 세금이 더 크게 발생하며 기본 RAG보다 못한 성적을 거두었습니다.

2. LLM의 자체 요약이 위험한 이유 (메모리 세금의 원인)

나중에 사용자가 무슨 질문을 할지 모르는 상태에서 LLM이 미리 원본을 손대면 크게 세 가지 문제가 발생합니다.

- 디테일의 영구 손실(충실도 저하): LLM은 요약할 때 큰 맥락만 남기고 구체적인 숫자를 버리는 경향이 있습니다. 사용자가 "택시비가 60달러라 비싸다"라고 한 말을, 메모리 시스템(OpenViking)은 "가성비 교통수단을 선호함"으로 요약하며 60달러라는 핵심 숫자를 날려버립니다. 실제로 이 시스템은 원본 핵심 사실의 38.0%를 아예 메모리에 남기지도 못했고, 13.0%는 심각하게 훼손했습니다.
- 문장 변질과 파편화(접근성 저하): 정보가 남아있더라도 찾기가 더 어려워집니다. 자전거 수리비 총액을 묻는데 등 교체비(40달러)와 체인 교체비(25달러)가 별도 조각으로 쪼개져 일부가 검색에서 누락되거나, 가방이 '도착한 날짜(1/20)'를 '사용하기 시작한 날짜'로 LLM이 마음대로 바꿔 적어 오답을 유도합니다.
- 모델 변경에 취약(강건성 저하): 메모리 구축과 해석이 LLM에 의존하다 보니, 답변 모델을 작은 모델로 바꿨을 때 기본 RAG보다 성능 하락 폭이 훨씬 컸습니다.

이러한 현상은 대화형 에이전트뿐 아니라 과거 작업 궤적을 재사용하는 코딩 및 도구 사용 에이전트, 그리고 이전 화면을 기억해야 하는 비디오 생성 월드 모델에서도 동일하게 나타났습니다.

3. 에이전틱 원본 검색(RAG 2rd)의 압승

그렇다면 원본을 가공하지 않고, 질문이 들어왔을 때 에이전틱하게 원본을 두 번에 걸쳐 찾아오는 RAG(2rd)와 비교하면 어떨까요?

RAG(2rd)는 1차로 키워드(BM25)와 임베딩 하이브리드 검색을 한 뒤, LLM이 "이 정보로 충분한가?"를 스스로 판단해 부족하면 후속 검색어를 만들어 원본을 한 번 더 뒤지는 방식입니다.

LongMemEval-s 벤치마크(GPT-5.6 Luna 기준) 결과를 비교해 보시죠.

- RAG(2rd): 정확도 90.0% / 사전 구축 0.11시간(약 6.6분) / 구축 토큰 0개 (추론만 0.65M 토큰)
- A-Mem(Flat 메모리): 정확도 84.0% / 사전 구축 117.0시간 / 총 174.7M 토큰 소모
- MemoryOS(계층형 메모리): 정확도 80.0% / 사전 구축 126.5시간 / 총 71.8M 토큰 소모
- MAGMA(그래프 메모리): 정확도 76.0% / 사전 구축 103.2시간 / 총 80.6M 토큰 소모

복잡한 메모리 시스템들이 LLM을 10만 번씩 호출하며 100시간 넘게 메모리를 구축하는 동안, 원본을 그대로 두고 질문 시점에 두 번 검색하는 RAG(2rd)는 100분의 1도 안 되는 비용으로 압도적 1위(90.0%)를 차지했습니다.

참고로 기본적인 RAG를 1번만 진행하는 RAG(1rd)도 정확도 82.0%로 뛰어난 성능을 보여줍니다.

4. 해결책: 원본 복구 경로와 검색 경험의 재사용

연구진은 메모리 세금을 줄이기 위해 기존 시스템에 바로 적용할 수 있는 간단한 해결책을 제안합니다.

- 원본 복구 경로 유지(+ src-aug): 요약된 메모리의 손실을 막을 수 없다면, 질문에 답할 때 가공된 메모리와 원본 기록을 함께 검색해 리랭킹하는 것입니다. 이 간단한 안전망만 추가해도 SimpleMem의 메모리 세금이 12.0%에서 5.2%로 절반 이상 줄고, 정확도는 73.6%에서 82.8%로 크게 뛰었습니다.
- 검색 경험의 재사용(+ recursive): 에이전틱 검색처럼 질문이 들어온 뒤 여러 번 검색하면 정확하지만 응답 지연(Latency)이 길어집니다. 이를 보완하기 위해, 과거 질문과 그때 어렵게 찾아낸 단서 자체를 다시 메모리에 넣어두어 다음번 비슷한 질문에서는 한 번에 찾도록 만들자 성능이 일관되게 향상되었습니다.

마치며:

이전 논문도 이번 논문도 RAG에서 원본을 보존하는 것이 가장 중요하다는 것을 알려줍니다.

이번에는 에이전틱하게 2단계로 실험을 했지만, LLM이 "이 정보로 충분하다"라고 판단할 때까지 루프를 도는 방식의 성능과 한계점도 실험했으면 좋겠네요.

더 나아가 text2sql이나 에이전트가 직접 Bash의 grep처럼 키워드 검색이나 문맥 확장 툴을 반복 호출하며 탐색하는 에이전틱 방식과의 비교도 후속 연구로 다뤄지길 기대해보겠습니다.
